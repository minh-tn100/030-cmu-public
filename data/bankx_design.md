# Bank X: a synthetic design for benchmarking

**Nature:** entirely synthetic. It does not describe the systems of any real bank. Its purpose is to give DesignBench a checkable input. The design deliberately mixes weak points, sound points, and points with too little information, so the agent has to be able to say "not assessed".

The machine-readable claims are in `bankx_claims.json`; the author's labels are in `golden_findings.json`.

## 1. System description

Bank X lets retail customers use a **Payment Agent** that pays on their behalf through chat. The agent reads the customer's request and the invoice sent by the payee, calls a payment tool, works with a **Fraud-Check Agent**, and stores customer preferences in long-term memory. The customer grants authority through a mandate (limit, validity period), following the delegation model of agent payment protocols. Components: Payment Agent, Fraud-Check Agent, Tool Gateway (`initiate_payment`, `get_fx_rate`, `run_reconciliation`), Memory Store, Agent Registry (if any).

## 2. Checkable claims

| ID | Design claim | Expected ASI | Author label (verdict) |
|---|---|---|---|
| C01 | Customer chat messages and invoice text supplied by the payee are placed in the same model context, with no separation of instructions from data. | ASI01 Agent Goal Hijack | gap |
| C02 | The `initiate_payment` tool is granted to the agent with a single permission: any amount, any payee, with no per-call limit check. | ASI02 Tool Misuse and Exploitation | gap |
| C03 | An approval token issued at the start of a payment stays valid for 24 hours and is not re-checked when the customer lowers the mandate limit. | ASI03 Identity and Privilege Abuse | gap |
| C04 | The MCP server that provides FX rates is loaded at runtime from a public registry, with no signature and no pinned version. | ASI04 Agentic Supply Chain Vulnerabilities | gap |
| C05 | Reconciliation scripts generated by the agent run in a sandbox with no network access, write access only to a temporary directory, and a timeout that kills them. | ASI05 Unexpected Code Execution | ok |
| C06 | Long-term memory stores payee details and preferences inferred from conversations; entries are written without provenance and without review. | ASI06 Memory and Context Poisoning | gap |
| C07 | Messages between the Payment Agent and the Fraud-Check Agent are mutually authenticated, digitally signed and carry a nonce against replay. | ASI07 Insecure Inter-Agent Communication | ok |
| C08 | If the Fraud-Check Agent fails, the Payment Agent retries up to 10 times and then automatically approves the payment to preserve customer experience. | ASI08 Cascading Failures | gap |
| C09 | Payments above a threshold need explicit customer confirmation showing payee, amount and the source of the instruction; the agent's reasoning is shown in plain text. | ASI09 Human-Agent Trust Exploitation | ok |
| C10 | There is no inventory of agents, any team can register a new agent, and there is no kill switch for a misbehaving agent. | ASI10 Rogue Agents | gap |
| C11 | Customer data is encrypted at rest. | no clear ASI | not_assessed |

## 3. Label mix

7 gap, 3 ok, 1 not_assessed. These are **the author's own labels**, used as the "gold answers" for evaluation; every evaluation report must say so. No independent second labeler yet.

## 4. Open review questions (author)

1. Is each claim worded clearly enough to admit one reasonable verdict?
2. Is the 7/3/1 mix right, or should harder cases be added (ambiguous claims, two ASI controls involved)?
3. Should claims tied directly to AP2 mandates (open/closed) be added? Note that the AP2 passage in the 3.1 corpus was unverified and used older terminology.
